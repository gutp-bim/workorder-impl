⚠テストの限界（事実と仮定の区別）

仮定 1: obs-analyzer のルール動作 — test_iot_to_wo.py は gutp:SmokeAlarm/event_state=ACTIVE で Issue が生成されることを前提とする。obs-analyzer の評価ロジック（閾値）は E2E 作成時に直接確認しておらず、ルール変更でフレーキー化し得る。
仮定 2: 非同期タイミング — Report→Issue の status が Open/PendingReview どちらになるかは NATS 配信タイミング依存。テストは条件分岐で吸収しているが、本質的にフレーキーリスクを内包。
未検証領域 — 永続化（再起動でデータ消失する前提なので「永続性」自体がテスト対象外）/ 同時実行・競合 / 負荷 / NATS 再配信時の冪等性 / 認証 / 障害注入。

③本番運用に向けた追加開発の必要性

機能正当性は確立済み。本番化のギャップは「非機能要件」に集中する。影響度と緊急度で分類した。

カテゴリ現状必要な追加開発優先度
永続化全サービス インメモリ dictDB 化（PostgreSQL 等）+ マイグレーション。再起動でデータ消失するため最優先必須
認証 / 認可全エンドポイント無防備OAuth2/JWT、サービス間 mTLS、RBAC必須
冪等性NATS 再配信の重複対策なしイベント ID ベース冪等キー、デデュープ層必須
耐障害性NATS at-most-once、DLQ 無しJetStream（永続化・再配信）、Dead Letter Queue必須
可観測性ログのみ構造化ログ、メトリクス（Prometheus）、分散トレーシング高
設定管理env 変数、obs-analyzer 閾値ハードコード設定ストア化、ホットリロード高
ビル OS 連携REST のみ、wo-scheduler の topology 未配線gRPC/MQTT コネクタ、performed_at へ Space ID 注入中
E2E 自動化手動トリガーのみdocker 対応ランナーで定期実行、フレーキー対策中
スケール単一インスタンス前提水平スケール検証（notify は queue group 済）低
スキーマ進化OWL タイポを実装側で吸収オントロジー上流修正 + 契約テスト低
なぜ「永続化」が最優先なのか — 派生する設計判断

インメモリ dict から DB へ移行すると、以下が連鎖的に必要になる:

  • トランザクション境界の設計（Issue→Ticket→WO は分散トランザクション or Saga）
  • イベント発行と DB コミットの整合（Outbox パターンが有力）
  • 冪等性（再配信時に DB 制約で重複を弾く設計）
  • マイグレーション運用（Alembic 等）

永続化の設計判断が冪等性・耐障害性のアーキを規定するため、本番化の出発点。

◆判断と推奨

問い回答
機能は正しく動くか？はい — 73 ユニット + 4 E2E で業務連鎖を立証済み
このまま本番投入できるか？いいえ — 永続化・認証・冪等性が無く、再起動でデータ消失・無防備
アーキ検証の目的は達したか？はい — SoS の連鎖設計と疎結合が実装で実証された
次に何をすべきか？永続化層の設計 → 冪等性 → 認証 の順で非機能を積み上げる
推奨 — 本実装は「アーキ検証 PoC として完成」と位置づけ、本番化フェーズを別マイルストーンとして切り出す。 まず「永続化＋冪等性」を 1 サービス（例: wo-manager）で縦に貫通させ、パターンを確立してから横展開するのが安全。
